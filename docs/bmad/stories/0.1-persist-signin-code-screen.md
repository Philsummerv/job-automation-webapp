# Story 0.1 — Keep the sign-in code screen alive when the browser reloads

## Status

Implemented — awaiting QA and a human pass on AC-1..7

## Story

**As a** first-time visitor who arrived from a Facebook post on my phone,
**I want** the "enter your code" screen to still be there when I come back from my email app,
**so that** the code I just went and fetched is actually usable and I can get into the product.

## Why this is Story 0.1

Every first-time user arrives on a phone, inside Facebook's in-app browser
(WKWebView on iOS). Sign-in is an emailed 6-digit code — there is deliberately
**no magic link** in the email (`docs/email/otp-code.html` line 10 says so
explicitly: *"Do NOT add {{ .ConfirmationURL }}. Its presence is what makes
Supabase send a link"*). So the only way in is: type email → leave the browser →
read the code in the mail app → come back → type the code.

Leaving the browser is the part that breaks. Facebook's webview routinely
reloads or discards the page while it is backgrounded. Every piece of state the
code-entry screen depends on lives in `useState` and nothing else, so a reload
throws all of it away. The user comes back holding a valid code and finds the
plain email form, with an empty email box and no code box at all. There is no
recovery path. This is the first thirty seconds of the product for every user
we acquire.

## Acceptance Criteria

Each of these is checkable by a human in a desktop browser in under five minutes.
"Hard reload" means Ctrl+Shift+R (or Cmd+Shift+R), which is the desktop stand-in
for Facebook's webview discarding and re-creating the page.

1. **The panel survives a reload.** On `/login`, type an email and press "Email
   me a sign-in code". Once the green "Check … for your sign-in code" panel
   appears, hard-reload the page. The green panel and the code input come back,
   and the panel still shows the same email address.

2. **A code fetched before the reload still works.** Do AC-1 for real with an
   email you can read, then after the reload type the 6-digit code from the
   email and press Sign in. It signs you in and lands you on the redirect
   target. (This is the whole point of the story: it proves `email` was restored
   accurately enough for `verifyOtp` at line 63.)

3. **"Use a different email" is visible and works.** The rehydrated panel shows a
   clearly visible control — a link or button, wording is Dev's call, e.g. "Use a
   different email" — that returns to the email form with the field editable.
   After using it, hard-reload the page again: you stay on the email form. The
   panel does **not** come back.

4. **Signing in clears the stored state.** After a successful sign-in (AC-2),
   navigate back to `/login` and hard-reload. You get the plain email form, not a
   stale code panel. (Devtools check: the storage key we added is gone.)

5. **Stale entries expire.** In devtools, edit the stored value's timestamp to
   something older than the expiry window, then reload `/login`. You get the
   plain email form, and the stale entry is removed from storage rather than left
   behind.

6. **The form is unchanged when storage is unavailable.** In devtools, block
   storage for the site (Chrome: Application → Storage → check "Block site data",
   or use a browser profile with all cookies and site data blocked; Safari:
   Private Browsing). Load `/login` and run the normal flow: type email → send →
   panel appears → enter code → sign in. Everything works exactly as it does
   today. No unhandled exception in the console, no blank page, no error banner
   the user did not cause. The only lost behaviour is that the panel does not
   survive a reload.

7. **No hydration error.** Load `/login` with the console open, with a stored
   entry present from step 1. There is no React hydration warning
   ("Hydration failed…", "Text content did not match…") in the console. The page
   may briefly render the email form before switching to the code panel — that is
   correct and expected.

8. **`npm run typecheck` in `apps/web` passes.**

## Dev Notes

### Use `localStorage`, not `sessionStorage`

`sessionStorage` is scoped to a single browsing context and dies when that
context is torn down. The exact failure we are fixing is Facebook's webview
**discarding** the page — the case where the context is torn down. `sessionStorage`
would survive an ordinary soft reload and lose everything in the one case that
actually costs us the user. Use `localStorage`.

The cost of `localStorage` is that the email address lingers on a shared device.
AC-4 (clear on success), AC-3 (clear on "use a different email") and AC-5
(expiry) between them keep that to minutes, and an email address is the least
sensitive thing here — no code and no token is ever stored.

### Expiry: 30 minutes

Supabase's default email-OTP lifetime is one hour, and there is no override in
this repo (no `supabase/config.toml`; the setting lives in the hosted dashboard),
so treat one hour as the ceiling.

30 minutes is the recommendation:

- It is far longer than the real round trip — switch to the mail app, hunt
  through spam, come back — which is a couple of minutes even when it goes badly.
- It stays inside the code's own one-hour lifetime, so we rarely restore a panel
  for a code that is already dead server-side.
- It rules out the "stored three days ago" resurrection outright.

If a restored panel does outlive the code, the failure is already handled
gracefully: `verifyCode` (lines 71-77) prints *"That code is invalid or expired.
Request a new email and use the code from the latest one."*

Store `{ email, sentAt }` where `sentAt` is `Date.now()`. On mount, restore only
if `Date.now() - sentAt` is under the window; otherwise remove the key. Put the
window in a named constant next to the storage key, not inline.

### Shape of the change

- One namespaced key, e.g. `jaui.login.pending`. Match the naming style already
  used for `GATE_KEY` in `AssistantChat.tsx`.
- **Write** on the success branch at line 51, alongside `setStatus("sent")`.
  Nothing is written on the error path.
- **Restore** in a `useEffect(..., [])`, never during render (see hydration
  below). Set `email` and `status: "sent"`. Do **not** restore `code` — the user
  is about to type it.
- **Clear** in three places: after a successful `verifyOtp` (before the
  `window.location.assign` at line 80), on the new "use a different email"
  action, and when the entry is found to be expired.
- Parse defensively. `JSON.parse` of a hand-edited or truncated value must not
  throw out of the effect; a malformed entry is treated as no entry and removed.
  Validate that `email` is a non-empty string and `sentAt` is a finite number
  before trusting them.

### Storage can throw on read, not just on write

In Safari private mode and in storage-blocked contexts, touching
`window.localStorage` can throw on **access**, not only on `setItem`. Wrap every
read, write and remove in its own `try/catch`. Do not hoist
`const ls = window.localStorage` outside a `try`. AC-6 is the check for this, and
`AssistantChat.tsx` lines 62-81 is the pattern to copy, comment style included.

### Hydration (Next.js 15, React 19)

`LoginForm` is a Client Component but it is still server-rendered, and
`localStorage` does not exist on the server. Reading it during render — including
in a `useState` initializer — produces a server/client mismatch and a hydration
error. Read it inside `useEffect` only. The one-frame flash of the email form
before the panel appears is acceptable and is stated in AC-7. Do not add
`typeof window !== "undefined"` checks in render as a workaround; that produces
exactly the mismatch we are avoiding.

### The "use a different email" escape hatch (AC-3)

Without it, a restored panel is a trap: someone who typo'd their address, or is
signing in as someone else on a shared phone, has no way back to the email field
short of clearing site data. It must be visible on the panel, not hidden. It
should clear the stored entry, reset `status` to `"idle"`, clear `code` and
`error`, and leave the email field editable (prefilling it with the stored
address is fine and probably kinder — Dev's call).

### Checked: Supabase's own client state is **not** a second, independent failure

Worth stating because it would have made this fix insufficient. It does not.

- `verifyOtp` does **not** use PKCE. In
  `node_modules/@supabase/auth-js/dist/main/GoTrueClient.js` (from
  `@supabase/supabase-js` ^2.47.10), `verifyOtp` begins at line 1964 and does a
  plain `POST` to `${this.url}/verify` with the params it was handed plus a
  captcha field. There is no `code_verifier` in that request, and no read of the
  stored verifier. Compare `exchangeCodeForSession`, which does read one (same
  file, ~line 1549: `if (!codeVerifier && this.flowType === 'pkce')`).
  **Consequence: email + 6-digit token is all the client needs. Restoring `email`
  genuinely completes the fix.**
- The Supabase session itself is kept in **cookies**, not `localStorage`.
  `@supabase/ssr`'s `createBrowserClient`
  (`node_modules/@supabase/ssr/dist/main/createBrowserClient.js`) builds its
  `storage` via `createStorageFromOptions` — cookie-backed — and passes
  `flowType: "pkce"`, `persistSession: true`. So blocking `localStorage` (AC-6)
  does not break the resulting session, and our new `localStorage` use cannot
  collide with Supabase's keys.
- One real caveat, and it is a caveat about the *magic link*, not about this
  story: `signInWithOtp` **does** write a PKCE code verifier into that cookie
  storage (`GoTrueClient.js` lines 693-697). If the webview drops cookies, a
  magic link would fail at `exchangeCodeForSession` in
  `apps/web/app/auth/callback/route.ts` line 24. The 6-digit code path has no
  such dependency. That is a point in the code path's favour and is worth knowing
  before anyone decides the Out of Scope item below.
- If cookies are blocked outright, sign-in cannot persist at all — but that is
  true today, is unrelated to this change, and is not this story's problem.

## Out of Scope

- **Re-adding a magic link to the email as a second way in. This is a separate
  decision for the owner, not a dev call, and must not be folded into this
  story.** The machinery already exists and is untouched:
  `apps/web/app/auth/callback/route.ts` handles `?code=…` via
  `exchangeCodeForSession` (line 24) and `sendMagicLink` already passes an
  `emailRedirectTo` pointing at it (`LoginForm.tsx` line 44). What is missing is
  only `{{ .ConfirmationURL }}` in `docs/email/otp-code.html`, whose header
  comment (line 10) says leaving it out is deliberate — adding it changes which
  Supabase template fires. The email subject and body are settled ground the
  owner does not want reopened. **Do not edit `docs/email/otp-code.html` in this
  story.** See also the PKCE-cookie caveat in Dev Notes: a magic link is *more*
  fragile in this webview than the code is, not less.
- Changing the email template, subject, or any copy inside it.
- Rate limiting, resend buttons, or a resend cooldown timer.
- Remembering the email address across sign-ins as a convenience feature
  (a "remember me" prefill). This story stores it only while a code is in flight.
- Any change to `safeRedirect` (`LoginForm.tsx` lines 16-21) or to the redirect
  handling.
- Persisting the typed `code` itself. Do not store it.
- Automated tests. There is no test runner in `apps/web` (`package.json` has only
  `dev`, `build`, `start`, `typecheck`), and standing one up is its own story.
  Verification for this one is the manual ACs plus `npm run typecheck`.

### Checks that came back clean

- **Storage safety.** Three separate `try/catch` blocks, one per operation.
  Nothing hoists `window.localStorage`. `readPending`'s second `try` wraps only
  the parse and validation, which touch no storage — so a parse throw can never
  be mistaken for a blocked-storage throw. No path lets a throw escape into the
  render or the effect. `writePending` sits inside an `async` handler, where an
  escaping throw would have killed `setStatus("sent")`; it cannot throw.
- **Malformed input.** Fed every case by hand: `null`, `"null"`, `"[]"`, `"{}"`,
  a truncated string, `{"email":"","sentAt":1}`,
  `{"email":"a@b.c","sentAt":"x"}`, `{"email":"a@b.c"}`. All return `null`.
  Nothing throws and no bad state is ever restored.
- **Clear paths.** All three required clears are present (success, switch email,
  expiry). A **failed** verify deliberately keeps the entry, which is correct —
  the user needs to retry the code they are holding.
- **Regression.** `safeRedirect` untouched. The `type: "signup"` retry untouched.
  The expired-code error branch (lines 175-182) untouched. `git status` shows
  `LoginForm.tsx` as the only modified file, so nothing in Out of Scope was
  touched — `docs/email/otp-code.html` in particular is untouched.
- **No key collision.** `jaui.loginPending` does not clash with
  `jaui.assistantGate` (`AssistantChat.tsx:39`, sessionStorage) or
  `jaui.betaBarDismissed` (`BetaBar.tsx:7`).
- **Dev Agent Record claims.** Spot-checked every one. All true, including the
  broken root `lint` script (`package.json:15` delegates to `apps/web`, which has
  no `lint` script) and the `/login` static-prerender claim. `switchEmail` is
  correctly not `use`-prefixed, so rules-of-hooks is not tripped.

### Non-blocking notes

1. **A malformed entry is never removed.** Dev Notes line 209 asks for "treated
   as no entry **and removed**". `readPending` does the first half and returns
   `null`, leaving the junk key in storage indefinitely. Nothing bad is ever
   restored from it, so this is cosmetic — but it is a real deviation, and it is
   what makes note 2 bite. One-line fix: `clearPending()` on each `return null`
   after a non-empty `raw`.
2. **AC-5 has a tester trap, caused by note 1.** When you hand-edit `sentAt` in
   devtools you must keep it a JSON **number** (`"sentAt":0`). If you type it
   quoted (`"sentAt":"0"`) the entry is malformed, not stale: you will get the
   plain email form (first half of AC-5 looks right) but the key will **still be
   there** (second half looks wrong), and you will log a false FAIL. Test AC-5
   with an unquoted number.
3. **`switchEmail` does not reset `verifying`, and a verify in flight is not
   cancelled.** Click "Sign in", then click "Use a different email" inside the
   ~1s request window. If the old request then succeeds, `window.location.assign`
   still fires and signs you in as the address you just asked to leave — on a
   shared device that is exactly the case the escape hatch exists for. If it
   fails, `setError` writes an error the email form never displays (line 267 only
   renders it when `status === "error"`), so it is silently swallowed. Narrow
   race, needs a valid code and precise timing. The proper fix is a generation
   or ignore flag in `verifyCode`, not a bare `setVerifying(false)` — which is
   why I did not patch it. Worth fixing later.
4. **A restored panel suppresses the `?error=auth` banner.** If someone lands on
   `/login?error=auth` (from `auth/callback/route.ts:30` or
   `auth/confirm/route.ts:22`) while a pending entry is live, the effect sets
   `status: "sent"` and the amber "that link expired" notice never shows, because
   line 247 gates it on `status === "idle"`. Arguably an improvement — the code
   panel is the more useful screen and the code is probably still valid — and
   near-unreachable in production anyway, since the email deliberately carries no
   link. Noting it so it is a decision, not a surprise.
5. **No length cap on the restored email.** A hand-planted megabyte string passes
   validation ("non-empty string") and gets rendered into the panel. Devtools-only
   and cosmetic; React escapes it, so there is no injection.
6. **Pre-existing, not this story: `BetaBar.tsx:20,24` touch
   `window.localStorage` with no `try/catch` at all.** It does not render on
   `/login` (it is mounted only in `app/(app)/layout.tsx:85`), so AC-6 on the
   login page itself is safe. But it *does* render on `/dashboard`, so a tester
   running AC-6 in a storage-blocked profile will hit a genuine uncaught
   exception the moment sign-in lands them there. Scope AC-6's "no console
   exception" to `/login`. This is a real pre-existing bug and deserves its own
   small story.

   re-rejected on every page load. This is what Dev Notes asked for, and it also
   removes the AC-5 tester trap Quinn found — a quoted `"sentAt":"0"` no longer
   leaves the key behind and read as a false FAIL.

2. **The abandoned-verify race is closed.** Added `attemptRef`, bumped by
   `switchEmail`. `verifyCode` captures it before awaiting and drops the result if
   it changed while the request was in the air, so pressing "Use a different
   email" mid-verify can no longer sign the user into the address they just left.
   `switchEmail` also resets `verifying`. Quinn was right that a bare
   `setVerifying(false)` would not have been enough — the generation guard is what
   actually prevents the sign-in.
